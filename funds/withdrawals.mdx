## Withdrawal flow

1. Read the withdrawable balance.
2. Confirm the destination chain and asset are available.
3. Request a withdrawal nonce and quote.
4. Build a domain-separated wallet message.
5. Ask the user to verify receiver, asset, amount, fees, and destination chain.
6. Submit the signed request with an `Idempotency-Key`.
7. Track internal review, source settlement, cross-chain messaging, and destination execution.

## Status is not binary

A cross-chain withdrawal may pass through:

`PENDING_RISK → APPROVED → SOURCE_PROCESSING → MESSAGE_IN_FLIGHT → DESTINATION_PROCESSING → CONFIRMED`

Return a machine-readable `reason_code` whenever the withdrawal is delayed, rejected, or fails.

<Warning>
  Never sign a withdrawal payload that omits `builder_id`, `chain_id`, receiver, asset, amount, nonce, and expiration.
</Warning>
